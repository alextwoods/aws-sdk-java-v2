Arms: `baseline` = published v2 2.46.10, `bridge` = `errbridge8` (ee9a74f69db-dirty), the tree with the
inert transport-retry change reverted. 23 cases, 2 reps, port 19082.

**This is the reference run for the branch's error behavior.** Byte-identical outcomes to `errbridge6`

## Result

Full diff, generated by `analysis/scripts/error_behavior_diff.py`, is in `diff.md`. That script is the
canonical count and this section quotes it.

- **Rep-to-rep differences: 0.** Every outcome is deterministic.
- **21 of 23 cases match on attempt count and outcome.**
- **20 behavioral differences**, plus **14 message-wording differences** reported separately.

The split matters and is the script's, not an editorial choice: `message` is compared but kept out of the
behavioral count, because SDKs reword messages without changing behavior and 14 rows of wording churn
would bury the 20 that mean something. Earlier revisions of this file and of `RESULTS.md` cited "34 field
differences", which is these two classes added together; the two numbers describe the same run.

### The 2 cases that differ in retry behavior

Both are `connection-reset`, and both for the structural reason in ledger 3.6: smithy-java drives its
retry loop from inside `ClientPipeline.deserialize`, which a failed send never reaches.

| | baseline | bridge |
|---|---|---|
| attempts, persistent | 3 | 1 |
| attempts, transient (3rd would succeed) | 3, **ok** | 1, **throw** |

Not fixable from the bridge; see run `20260905-0246` for the fix that was tried and measured inert.

### The rest, by field

| field | count | class | cause |
|---|---|---|---|
| `rawResponse` | 10 | behavioral | `awsErrorDetails().rawResponse()` never populated (ledger 1.4) |
| `exception` | 3 | behavioral | `conditional-check-failed` → `DynamoDbException` (ledger 1.3); 1 is `connection-reset` |
| `cause` | 3 | behavioral | `SerializationException` vs `UncheckedIOException` (ledger 3.5); 2 are `connection-reset` |
| `attempts`, `outcome`, `retryable` | 4 | behavioral | all `connection-reset` |
| `message` | 14 | wording | `(SDK Attempt Count: N)` suffix absent; 2 cases also drop the service's message text |

Of the 20 behavioral, **13 are metadata a caller reads after the fact** — `rawResponse` (10) and the two
type mismatches (3) — and **7 are `connection-reset`**, which contributes rows across six fields because a
lost retry changes the attempt count, the outcome, the exception, the cause, and the retryable flag at
once. Nothing in the first group changes what the pipeline *does*; all of the second group is one defect.

### Backoff timing — resolved elsewhere

`diff.md` also flags 11 cases whose wall time differs by 2x or more, the worst being
`throughput-exceeded` at 2,785 ms baseline vs 729 ms bridge when persistent and 346 vs 2,632 — reversed —
when transient. **None of it is a signal, and none of it is claimed here.** This run uses v2's default
full-jitter backoff at 2 reps, where a throttled 3-attempt call is uniform on roughly `[0, 3 s)`, so a 4x
spread in either direction is the expected behavior of identical policy.

It is resolved by construction rather than by more reps: `javap` shows `SdkRetryStrategy` delegating delay
computation to the wrapped v2 strategy wholesale, so the arms cannot differ on delay. `20260905-1527`
confirms it empirically with the jitter removed (203.0 ms per extra attempt in every arm at a configured
200 ms), and `20260905-1532` measures what retrying actually costs. The `wall_ms` column in *this* run
should be read as nothing at all.
