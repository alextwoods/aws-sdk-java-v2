## Decision applied: Rejected (REVERT)

The keep rule needs every target to gain beyond its floor. The two v2-async targets did: small-get saved 261 B/op
(−0.5%, floor 0.2%) and small-put 188 B/op (−0.4%, floor 0.2%). The two v2-sync targets did not: small-get saved
123 B/op (−0.2%, floor 0.5%) and small-put 51 B/op (−0.1%, floor 0.9%). No guard regressed beyond its floor, no run
failed, every case has a floor, and the widest target floor is 0.9%. That is the README's Rejected case (some
targets gained, but not all), so the row in `racecar-decisions.yaml` is now `Rejected` with these numbers.
`cand/E13` is not merged.

One CPU metric moved beyond its floor, in the improving direction: v2-async small-get application CPU −4.9% against
a 3.5% floor. Guards only check regressions, and one case past its floor is not a CPU claim. v2-async small-put
moved −2.0% (floor 2.3%), and v2-sync small-get and small-put moved +0.4% and −0.2%.

For scale: racecar's allocation profile put the removed `doApplyInterceptorModifiedProperties` subtree at 360 B/op
(sync) and 225 B/op (async), and the laptop smoke (`E13-smoke.md`, 2 × 300 operations) saw −356 and −296 B/op on
small-get. On the metal host at 7 × 50,000 operations the saving is 123 (sync) and 261 (async) B/op on small-get and
51 and 188 B/op on small-put, 0.1–0.5% of about 48–54 KB/op.

## Combined design: E13 and smithy-java `1f68318ce`

The plan paired E13 with smithy-java `1f68318ce` ("Skip auth scheme property merge when the option carries no
overrides"). Upstream, `ClientPipeline.withOverrides` returns the auth scheme's base context when the option's
override context is `Context.empty()` (an identity check), instead of merging it. The rest of that commit is
Javadoc (`Signer`, `IdentityResolver`, `AuthScheme`, `Context.empty`) and a test.

- **V2's equivalent** is the other per-call option copy, `AuthSchemeResolver.mergePreExistingAuthSchemeProperties`,
  called from `AuthSchemeResolutionCache.resolve`. When the pre-interceptor snapshot holds the same option as
  `SELECTED_AUTH_SCHEME` (no interceptor changed it), it always runs `toBuilder()` on the resolved option, a
  `putSignerPropertyIfAbsent`/`putIdentityPropertyIfAbsent` for each property of the existing option, `build()` and
  a new `SelectedAuthScheme`.
- **Planned combined design:** E13 unchanged, plus a lazy copy in that branch. Walk the existing option's
  properties, create the builder only at the first key the resolved option does not contain (exact presence, since
  `putIfAbsent` treats a key with a null value as present), and return the resolved `SelectedAuthScheme` itself
  when no key would be added.
- **Probe result: the merge half cannot help on the harness calls**, so it was dropped before measuring, as the
  plan prescribes. A DynamoDB client built like the harness's (us-east-1, static credentials, standard retry, a stub
  HTTP client), run with the feature jar, printed the options on 2 GetItem and 2 PutItem calls. On every call:
  - the resolved option held 2 signer properties, `ServiceSigningName` and `RegionName`;
  - the pre- and post-interceptor snapshots were the same instance, the `unset` placeholder, with 3 properties:
    `ServiceSigningName`, `RegionName` and `ChecksumAlgorithm` = null (`RESOLVED_CHECKSUM_SPECS` is mapped onto
    the placeholder's `ChecksumAlgorithm`);
  - the merged option had all 3.

  So the merge must add `ChecksumAlgorithm` on every harness call, and a lazy copy would still copy every time.
  Upstream's shortcut has the same limit: it skips only when there is nothing to merge.
- **What was measured:** E13 alone (`AuthSchemeResolver.applyInterceptorModifiedProperties`), the cherry-pick of
  `opt/E13`. The merge copy stays as it is. Removing it would need the placeholder not to carry a null
  `ChecksumAlgorithm`, or the resolved option to carry it. Either changes what `SELECTED_AUTH_SCHEME` holds, so it is
  a separate change and was not attempted.
